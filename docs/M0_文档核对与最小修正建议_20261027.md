# M0 文档核对与最小修正建议

核对日期：2026-10-27。依据：用户明确指定的两份 20261026 文档、当前工程源码及实际引擎验证。两份原文件保留在 Downloads，未改写。

本轮先完成用户追加的 UI 改版和独立回归，再进入 M0 Step 1。M0 阶段只产出现状、核对和验证记录；没有接入路由、表现模型，没有拆主场景，没有执行 M1–M7。文档中的“所有者已确认”属于设计文件的陈述，不被当作本轮新增授权。

## 按严重程度排序

### P0：SceneRouter 同名全局类与 Autoload 冲突，照抄会使单例编译失败

位置：M0 提示词第137行 `class_name SceneRouter`，第260行及附近注册同名 Autoload；项目目前没有这两个新骨架。

使用随工程 Godot 4.7，在工程外的最小临时项目中实际复现。错误为 `Class "SceneRouter" hides an autoload singleton.`，随后单例无法创建。该导入进程退出码仍为0，stderr有432字节，进一步说明验收不能只看退出码。

最小建议：保留 Autoload 名称 SceneRouter 及文件路径，去掉同名 `class_name`；类型需要明确时用预加载的脚本类型别名，避免同时占全局名称。这是接口声明修正，不改路由总体设计；尚未在正式工程实施，需所有者确认。

### P1：关闭期间“所有公开方法零副作用”与真实注册表相矛盾，现有 QA 不足以证明

位置：M0 第92行要求所有公开方法零副作用；第266行允许 register_screen/is_registered 真正操作内存字典；第283行要求注册后可查询。若“零副作用”包含对象内部状态，三者不能同时成立。

最小建议：明确为“ENABLED=false 时 change_scene 不加载、不实例化、不改树、不发信号、不更新 current_screen_id；注册方法只允许内存注册表变化，不读取资源、不触发生产行为”。is_registered 保持只读。

第284行仅比较 Main 直接子节点数量/名称，无法排除后代属性变更、资源加载、信号、孤儿对象或注册表污染。最小增强：保留原断言，再检查完整树的关键状态、信号计数、当前屏幕、注册表前后值及加载/实例化调用计数。不能称直接子节点计数为“零副作用硬证明”。这些是后续 Step 6–7 的契约选择，本轮未改实现。

### P1：ViewModel 预期 push_error 会击穿空 stderr 验收门槛

位置：M0 第167、251行指定基类 snapshot() 的 push_error；第287行又要求在成功 QA 进程调用它，并称可只验证返回{}；第26行定义通过条件为退出0且stderr为空。

工程外实际运行相同形状的基类调用：返回空字典为true、退出码0，但stderr有225字节。忽略返回值或错误文本不会消除 stderr；不能为了通过而删除全局 stderr 检查。

最小建议：成功 QA 主进程仅检查测试子类的 changed 与 snapshot 正常路径；基类抽象方法的预期报错放到独立负向子进程，捕获并严格匹配预期错误与返回值，并确保没有额外错误。原始stderr单独留档。另澄清第246/253行“没有任何子类/实例化”指生产代码，Step 7 的 QA 内测试子类允许存在。需确认后再写 Step 5–7。

### P1：依赖扫描范围不能覆盖工程，条数门槛也与过滤规则冲突

位置：M0 第222–240行。列出的目录没有完整包含当前 PvE/UI、Runtime/Behavior、Runtime/Callbacks、其他 Core 脚本、主场景动画 NodePath 与信号连接。新 UI 路由确实在 PvE/UI；把旧目录表当全集会漏掉拆场景时必须处理的引用。

最小建议：以工程全部生产 .gd/.tscn/.tres 与现有工具源码为初始全集，扫描 `get_node/get_node_or_null/$/%/NodePath`、Game 节点别名、相对路径、动画轨道与信号连接，再逐项标记“纳入 / 排除及原因 / 动态待人工确认”。保留不拆物品场景体系的边界，但跨入 Main 的物品引用仍要追踪。

第231行过滤无关命中，第240行却要求保留条目数不低于原始 grep 命中数；合理排除就可能违反后者。同一行多种命中也不能硬算为同一条依赖。建议改为“所有候选命中均有去向；候选=纳入+解释排除+待确认”，同时给出按目录统计、抽查文件及剩余动态引用。这个方案待确认；本轮只核对风险，没有冒充完成 Step 4 的全工程依赖清单。

### P2：性能口径可用于观察，尚不足以稳定判断退化

位置：设计方案第51行（静态内存+5%、帧间隔中位数+10%）；M0 第212、216行（两次较差值、2×12指标）；当前 LoadingProfileQA.gd 第22–48及65–86行。

实际采样脚本每个进程输出 title_initial、title_idle、shop、codex、codex_closed、title_returned 六个有标签阶段，各阶段包含十二项基础指标及流式加载等附加信息。不能压扁为一个进程只有十二个数；不同阶段不能交叉取最差后再比较。每阶段120帧的间隔不是CPU/GPU计算耗时，VSync或帧率上限能掩盖轻度退化，窗口后台限帧也会影响结果。当前返回标题使用异步方法但未显式 await，后续基线应记录是否跨过加载屏障，以免在卸载尚未完成时采样。

最小建议：保留两次独立进程的完整六阶段原始采样，按相同标签比较；固定引擎、渲染方式、分辨率、VSync/帧率上限、前后台状态、预热/冷热缓存、种子与测试负载，记录CPU/GPU/内存及采样时其他负载。先说明比较取值规则，较差基线会放宽允许退化范围，并非天然更保守；接近门槛时追加复测再判断。

不擅改既定+5%/+10%阈值，也不把本轮UI回归的一次LoadingProfile当成M0 Step 3的双次基线。上述口径须确认后执行 Step 3。

## 当前源码与文件中的其他偏差

- 真实 Autoload 为24个。M0 文件自身展示的有序名称也是24个，却写“共25个”。现状快照按实际摘录，未加虚构单例。
- verify_native.ps1 默认22个阶段；本轮独立验证另加入口启动，因此是23个进程。提示词所列旧名展开其实是32项，另文又写28项，不能把22或23写成31。旧阶段中若干场景/脚本已经不存在，不能照抄调用。
- 本轮默认UI阶段由旧MobileUIMain更新为TouchPagesMain；MobileUIMain仍是兼容入口。阶段数仍为22，设置/存档write→reopen顺序未改。
- 工程QA实际使用带窗口的 GL Compatibility 运行方式，公共脚本没有传 `--headless`。文档称其全为headless不准确；真实鼠标另用隔离测试窗口，公共默认22阶段不会自动移动系统鼠标。
- Main.tscn 实测仍为15072行，这一项与文件一致；场景总数、NativeExpedition行数、Runtime目录应以 Step 1 最新命令为准。当前场景已瘦身，不能沿用文档的1054场景总数。
- 461_Local参考工程和可用Python在本机实际存在，设计方案关于二者缺失的事实已过时；这不自动恢复硬匹配率门槛，门槛仍是需所有者决定的设计事项。
- RuntimeContractsQA.gd/RuntimeContracts.tscn作为提示词示范的路径在当前工程不存在；后续应以真实存在的LoadingContracts/TouchPages等模式重新核对，不能把不存在的范例视作已验证契约。
- M0产出目录沿用 `m0_baseline_20261026` 是计划指定名称；实际采集日期明确写2026-10-27，没有倒填日期。
